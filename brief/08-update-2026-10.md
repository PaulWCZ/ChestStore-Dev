work would run: the Chest posts runs elsewhere (below).

## The platform: what else changed

- **Custom domains for public parts exist** (and have since late
  September): the owner connects `status.acme.com` to a tool's public part,
  the Chest serves its certificate, and `chest.tool.publicUrl` says it. The
  critique's "custom domains" blocker for Status, Booking, Support and
  Hiring is gone; the email one stays.
- **Routing of static files — one rule (`build.static`).** On the tool's
  hosts, and in a Perseus preview, the Chest serves: `/chest…` to members
  (with `Chest-Member`); a **GET under a `build.static` prefix** as a
  static file, to anyone, without a member; everything else to the public
  part when `chest.json` says `"public": true`; **404 otherwise**. Up to 4
  prefixes, each `"/…/"`, `/_next/static/` when the key is absent; never
  `/chest/`, `/_chest/`, `/chest-events/`, `/chest-schedules/`. A
  private tool's stylesheet or script served outside `/chest` and outside a
  declared prefix loads in no page (found on 2 October with a draft that
  served `/assets/`).
- **Tools sleep when idle** and wake on the first request, event or
  schedule run (the test bench wakes in about 0.5 s; a request waits 60 s
  at most, a browser sees "Waking up…" after 2 s). Keep nothing in process
  memory that must survive; a cold start is part of the user's wait.
- **Memory**: 256 MiB per tool by default (512 or 1024 if the owner
  chooses), 1 CPU; the build container has 512 MiB and one CPU; the Chest
  reserves memory for awake tools only.
- **Logs**: a tool's stdout and stderr are its runtime log, kept 7 days
  (5 MiB then one previous file; a line is cut at 4 KiB), shown in its Logs
  tab, merged with the Chest's own in Settings → Logs, downloadable over a
  period, and read by agents with `GET /api/v1/logs`. Log what an operator
  needs to understand a failure; never a secret, a token or personal data.
- **HTML mails** — the Chest's own mails (invitations, codes, resets) are
  now text and HTML from one layout. This is **not** a tool capability:
  there is still no `mail` for tools (the mail connector, batch G, is not
  built).
- **Guest** is a member status (below member, listed apart: an outside
  accountant). Tools are told nothing new.
- **Perseus Code**, the Chest's build agent, builds tools inside the Chest
  from a conversation. Its drafts run in a workbench with their **own
  `CHEST_API`** (the draft API): three fake members, notifications kept in
  the draft, their own files, AI counted under the project, a database
  `pb_<project>`. Every new project starts from **the official starter**,
  `reference/perseus-starter/`: TypeScript, Hono, React rendered on the
  server with islands, Vite, a nonce CSP, a test; in the workbench, build
  0.6 s, cold start about 0.1 s, **about 72 MiB at rest**.

## The three asks

### (a) Every tool on SDK 0.4.x and the 0.4 manifest

Rebase `sdk/` onto `reference/sdk/` as you did for 0.3.0 (0.4.1 verbatim,
your proposals on top, `0.4.1-studio.N`), dropping what 0.4.x now gives and
adopting its shapes where they differ. Then every tool: `"chest": "0.4"`,
`schedules` in `chest.json` and `/chest-schedules`, the official
`chest.tool.*` and `chest.currency`, `build.static` checked against what the
tool serves; `chest check` must say OK for each, with only the official keys
in `chest.json`. Bring the harness to the 0.4 environment
(`CHEST_CURRENCY`, `CHEST_TEAM_URL`, `CHEST_PUBLIC_URL`). Rewrite the SDK
report's baseline (§2, §5, §10) against 0.4.1 and update the critique's
verdicts where a blocker is gone (custom domains).

### (b) Memory: the lighter stack, unless a tool has a measured reason

Measure each tool's memory at rest, the same way for all (say how), before
and after. Move the tools built on Next.js to the reference stack
(`reference/perseus-starter/`) unless a tool has a measured reason not to —
write the reason and the numbers in the report. Keep each tool's features,
tests, flows, audits and looks; the UI kit comes along.

### (c) A better starter template for Perseus

Perseus starts every tool from `reference/perseus-starter/`. Propose a
better one, as a deliverable: a report under `reports/` (for example
`reports/06-perseus-starter.md`) and a **working template folder** that
builds, tests and passes `chest check`. Judge candidates — the current
starter included — on memory at rest, cold start, simplicity for an AI
agent writing a tool in it, UI quality (the kit, themes) and accessibility,
with measurements. The owner decides what the Chest ships.

## Addendum 2026-10-06 — mail and notifications (owner's decisions)

These decisions are final; where the studio's code differs, the studio changes.

- **Mail to members is never a tool's job.** Every mail a tool sends today to
  a member (task assigned, leave approved, expense to review, poll opened, page
  changed, reminders…) becomes a notification: `notify` for one member,
  `broadcast` for everyone who has the tool or some of its groups/roles. The
  Chest itself mails members their notifications, by each member's choice
  (every notification, once a day, twice a day, or off; and off per tool).
  Drop `mailPreference`, member recipients in `mail.send`, and any digest or
  reminder mail a tool builds itself.
- **The Chest never receives mail.** No inbound mail, no mailbox, no reply
  threads. A tool that wants replies from the public shows or sets the
  company's own address (Reply-To); replies go to the company's usual mailbox.
- **Mail to the public is not a priority and never goes through the Chest or
  Argentic.** It will come later only through a connector to the company's own
  mail provider. Design public flows to work without mail: show the
  confirmation on the page, offer a calendar file or a link to download, and
  let a member follow up with the company's own mail. If a tool truly needs a
  mail to the public, keep it behind a clearly separated, optional seam and
  write the need in the SDK report — do not fake it.
- **Groups and broadcast** are being added to the official SDK (proposed 0.5):
  a `members.groups` capability, `member.groups`, `members.list({group})`,
  `notifications.broadcast(notice, {to, except})`, `translations` on notices.
  No fixed caps on members or groups: the server's capacity is the only limit.
  The reference will be refreshed when it is released.
