# The 18 tools on SDK 0.7.0: what works, and what is not possible

24 November 2026. The owner asked for every tool on SDK 0.7.0 (Chest-SDK PR #38, head
`1a825a6`, contract `"chest": "0.7"`). Where something is not possible, the owner
asked for a list of the reasons. This report is that list, with the tool and the code
that prove each item.

**Status.** All 18 tools declare `"chest": "0.7"`. They vendor `sdk/` =
`0.7.0-studio.2` (the official 0.7.0 byte for byte, plus the studio's proposals in
`client/studio/`) and the package `@argentic/chest-app` `0.1.0-studio.13`. Each tool
was migrated by one agent and reviewed by another, in groups of three. Every fix the
reviews asked for is merged.

**How it was verified.** Per tool:
- `npm test` passes on PGlite and on PostgreSQL 16 (Node 24).
- 0.7.0's `chest check` passes (`scripts/chest-check.mjs`). Warnings remain only on
  already-shipped migrations that drop a column without the new `-- chest: contract`
  marker; a shipped migration cannot be edited.
- `check-manifest` and `check-vendor` pass.

Browser flows and axe: see §6.

**Not verified.** How a real 0.7 Chest behaves beyond what the PR's code, README and
contract say. The studio's fake (`sdk/testing`) stands in for the Chest everywhere.

**Legend.**
- **Impossible:** 0.7.0 has no API, and no workaround fits the contract. The tool falls
  back as described: it never breaks.
- **Degraded:** possible on 0.7.0, at the cost stated.

In the studio, every impossible item still runs in tests through a studio proposal in
`sdk/client/studio/`, with its fake. On a real 0.7 Chest, those calls throw
`CapabilityNotGranted` or `Unavailable`, and the tool shows the fallback.

## 1. Currency and time zone: done in the tools, as the owner decided

0.7.0 has no `chest.currency`. `chest.timeZone` remains, read-only: it is the
company's reference zone, captured once from the owner's browser and set on no screen.
`member.timeZone` is the member's browser zone. Each tool now handles both itself.

| Tool | Currency | Zone |
|---|---|---|
| Quotes | Default currency setting. Each document, catalogue item and the share capital keep their own. Totals and revenue per currency | Company's day |
| Expenses | Reimbursement currency (the tool's own). Limits, flat rates and mileage keep a code (migration 0007) | — |
| Timesheets | One currency per tool. Changing it is refused once time is invoiced. 0008 takes the old currency from past hand-offs | — |
| Goals | A money key result keeps its own code. The tool has a default | — |
| Clients | Default for new deals. Imports read a currency column. Totals count the default currency and say how many deals are in others | — |
| Equipment | Each item and repair keeps its own. Old prices (0009) take the first currency a manager saves (0010) | — |
| Hiring | Salary currency, defaulting to the latest salary's, else the country's | — |
| Status | — | "Time zone of the page" setting, used on the public page, feeds, mails and API |
| Rooms | — | One zone per office (0013). Bookings keep their local time when it changes |
| Leave | — | Days follow the company's zone; hours follow the member's |

The rule everywhere follows the official Times table:
- "Today", deadlines and working days use the company's zone (`chest.today()`).
- A time shown to a member uses the member's zone.

The package dropped `f.today()`, which mixed the two.

**Studio convention.** An `amount` in an event between tools is in the currency's
ISO 4217 minor unit (0 decimals for JPY, 3 for KWD), with the code beside it. A review
found Quotes dividing a yen deal from Clients by 100 twice; that is now fixed and
tested.

**Impossible:** converting between currencies, because there are no exchange rates.
So Clients and Quotes never add amounts in two currencies.

## 2. Impossible on 0.7.0

### 2.1 Mail to people outside the company (9 tools)
Booking (guests), Quotes (documents to clients), Forms (a visitor's copy), Polls
(guests), Status (subscribers), Support (requesters), Hiring (candidates), People (the
welcome letter to a future hire's personal address), Rooms (visitors' invitations).
- **Proof:** `grep -rl "chest-sdk/mail" tools/*/*/src`. For example:
  - `tools/public-and-private/booking/src/lib/mailer.ts`
  - `tools/private/people/src/lib/welcome.ts`
  - `tools/private/rooms/src/lib/invitations.ts`
- **0.7.0:** members' notifications are mailed by the Chest. There is no send to anyone
  else.
- **Workaround:** each tool calling a provider's API itself, with its own key in `env`.
  That goes against the owner's one-connector decision, so it is not done. The studio's
  `mail` proposal (paced, refuses members' addresses) shows the API wanted.

### 2.2 One calendar feed per member, across tools (8 tools)
Tasks (due dates), Leave, Rooms, Booking, Hiring (interviews), Clients (next steps),
News and Polls (events).
- **Proof:**
  - `tools/private/tasks/src/lib/due-calendar.ts`
  - `tools/private/leave/src/lib/leave-calendar.ts`
  - `tools/private/rooms/src/lib/calendar.ts`
  - `tools/public-and-private/booking/src/lib/publish.ts`
- **0.7.0:** nothing.
- **Fallback:** the .ics download stays where it existed.

### 2.3 Another tool's address, and whether it is installed (5 tools)
- **Clients** cannot link a deal to the Forms answer or the booking it came from.
- **Timesheets** cannot link to the invoice in Quotes.
- **Forms** cannot tell "Support is not installed" from "not linked". It now guesses
  "not linked" when the last event of that kind reached no tool.
- **Quotes and Support** have the same need.
- **0.7.0:** a tool knows only its own address. `emit` returns a count, never names.

### 2.4 The store's words in French (all 18)
- **What fails:** title, description and role names exist in one language
  (`contract/README.md`), so a French member sees the tile, roles and store page in
  English.
- **Proof:** every `chest.proposals.json` keeps `translations.fr`.

### 2.5 The visitor on public pages (Booking, Forms, Polls, Quotes)
- **What fails:** no per-visitor rate limit on a public form, booking or guest answer,
  only a ceiling for everyone, which a robot can exhaust. A quote signed online records
  the visitor as "unknown" in its acceptance proof.
- **0.7.0:** the front adds no client address, and the tool must not trust
  `X-Forwarded-For`.
- **Studio proposal:** a Chest-held `Chest-Visitor` key (HMAC).

### 2.6 Status checks every 1, 2 or 5 minutes (Status)
- **Proof:** `tools/public-and-private/status/src/lib/checks.ts` (`everyChoices`).
- **0.7.0:** schedules run at least 15 minutes apart. A self-made check would also need
  `"network": ["*"]`, and would look from inside the company's own server.

### 2.7 Live public pages (Status, Support, Hiring, Booking, Forms)
- **0.7.0:** realtime serves members on the team host only.
- **Fallback:** the public status page keeps a one-minute refresh that stops when the
  visitor is idle. The other public pages need none.

### 2.8 To-do items (capability `todo`)
- **What 0.7.0 has:** the contract accepts the capability, and `chest check` passes it,
  but there is no SDK function, route or manifest key to put an item.
- **Tools that would use it:** Tasks (due), Leave and Expenses (approvals), Equipment
  (returns), People (onboarding steps).

### 2.9 The company's look across tools (all 18)
- **What fails:** no company theme. Each tool shows its own identity, which is its
  existing fallback.

### 2.10 Files a visitor may send (Forms, Support, Hiring)
- **What fails:** the Chest recognises a visitor's file by its bytes, and does not
  recognise `.txt`, `.csv`, `.doc` or `.xls`. Visitors can no longer send them; members
  still can.
- **Proof:** `tools/public-and-private/forms/src/shared/model.ts` (visitor types), and
  test `uploads.test.ts`, which grants every type offered.

## 3. Degraded on 0.7.0 (done, at a cost)

| Need (tools) | Done on 0.7.0 | Cost |
|---|---|---|
| Webhooks to Slack, Teams or any URL (Forms, Support, Status) | Studio proposal `webhooks: true`. The 0.7.0 path is `"network": ["*"]` + `fetch` | The owner approves "any host". Retries only at schedule times. The tool keeps the secret and the journal |
| Pictures on public pages (Forms headers, Hiring careers) | Studio proposal `files.publicFiles`. The 0.7.0 path is a public route streaming `files.get` | The bytes cross the tool, which wakes at every uncached view |
| Which addresses are members (Equipment's Intune match, People, Rooms) | Matching by name, or `members.email` | A wider permission than the need, or a weaker match |
| When a former member left (Expenses, Timesheets) | Recorded when `member.removed` arrives | Unknown for anyone who left before installation |
| Visitors' uploads that no answer claimed (Forms, Support, Hiring) | A daily sweep deletes them | The tool must list and compare |
| "Sent to N people" after a broadcast | Count with `members.list` beforehand | An estimate |
| Events with an underscore | Renamed on both sides: `people.leaving-cancelled`, `hiring.hire-cancelled`, `timesheets.billable-cancelled` | A coordinated change |
| Lists in event data (busy spans, form answers, invoice lines) | JSON inside a `text` field | Not typed or checked by the Chest |
| A form answer restricted to some people (Support) | Not filed: every agent reads the inbox | The answer stays only in Forms |
| A public page framed in another site (Status, Support) | The tool's list of sites plus the owner's allow-list in the Chest | Two lists to keep in step |
| An item restricted to some people inside a shared number (Goals) | A key result counts every item as a bare number, and shows no item outside its audience | A sum over one confidential item reveals it. Today Clients sends won deals to everyone |

## 4. Sealed values (brief 09)

| Tool | Sealed | Opened by |
|---|---|---|
| Expenses | IBANs (old AES values re-sealed nightly; plaintext `v0.` values stay for up to a day after upgrade) | Role `accountant`, on their request when downloading the transfer file |
| Hiring | Candidates' private notes; strengths and concerns in feedback | Members Hiring already lets read them, per request. A note is refused rather than stored in clear when sealing is unavailable |
| People | Home address, emergency contact, pending change requests | Role `hr`, plus a second copy for the person it concerns |

The other tools hold nothing that qualifies, or need the value in clear:
- Quotes prints the company IBAN on every invoice.
- Booking's scheduled reminders need the guest's details.
- Forms' exports, webhooks and events need the answers.

**Limits found:**
- **A seal names roles, never "the member it is about".** That is why People keeps two
  copies, and why an owner of an IBAN in Expenses sees it only masked.
- **A schedule cannot open a sealed value.** Opening needs a member's request, so
  nightly jobs can only re-seal.
- **Locked values are a UX trap.** Two reviews found forms that showed a placeholder or
  an empty field where a sealed value could not be opened, which a save would have
  written back. Both are fixed: Hiring blocks the form, People hides the fields.

## 5. Realtime (brief 09: no more polling)

Every tool's pages now follow realtime channels instead of refreshing on a timer. Two
exceptions remain:
- Status' public page (2.7).
- Wiki's editor, whose 30 s heartbeat is the lease of its edit lock.

**Contract rules met:**
- A table feeds one channel only.
- A feed targets a declared channel, or `prefix:{column}` of a channel joined through a
  membership table, never `{member}`.
- A membership table's key column must differ from its member column.

**Consequences:**
- A member's own rows ("My expenses", "My equipment", "My requests") are pushed by the
  tool with `publish`, not by a feed.
- A channel limited to "whoever may see this item" needs a membership table that the
  tool fills when it checks access, and empties wherever access changes. Wiki, News and
  Polls do this after review C, for any id a member could guess.

*The gating of the remaining shared channels (Tasks, Booking, Forms, Hiring, Goals,
Expenses) is being completed; this section is updated when it lands.*

**Wanted:** a join rule based on groups or on an audience column, so that tools need no
membership bookkeeping.

## 6. What the reviews caught

The reviews caught bugs that tests alone missed. They are listed as evidence for the
SDK report.

**Critical:** Quotes dropped every Timesheets hand-off. It required a `version` field
that Timesheets' declared schema does not have, so both test suites passed. The fake
does not check a receiver against the emitter's declared schema. Each tool now has a
test that delivers exactly what its partners declare.

**Event types name no tool.** Any linked tool could send `timesheets.billable`,
`quotes.invoiced` or `crm.deal.won`. Every receiver in all 18 tools now reads a type
only from the `source` its first word names.

**Format characters.** 0.7.0 refuses Unicode format characters in event `text`
fields, including the joiner inside common emoji, so a guest named "Nina 👩‍💻" was never
told to Clients. Every emitter now strips them, in the event only.

**Smaller fixes:**
- The Timesheets and Equipment currency migrations were blind.
- Clients showed yen and dinar with the wrong decimals.
- People and Hiring's locked forms (§4).
- Two Leave tests depended on today's date.
- A read and action race in the package (fixed in `studio.13`, with 12 new tests).

**Browser flows and axe.** During the migration, each group's flows and axe ran green
on a harness that the agent patched locally: lab/chest-dev could not start a 0.7 tool.
- Booking 38/38, Forms 31/31, Quotes 33/33.
- Expenses 34, Timesheets 25, Goals 32 steps.
- Rooms 39, Equipment 35, Clients 47.
- Tasks, People 43/43, Leave 45/46 (the fake's `former` limitation, §7).
- Polls, News, Wiki.

Axe found 0 violations on every tool. The shared harness is being moved to 0.7, with a
realtime relay. The final run of all 18 flows on it is recorded in `PROGRESS.md`.

## 7. For the SDK report (needs, beyond the impossibilities)

1. **A shared declared shape for paired events,** checked on both sides. Three
   receiver/emitter mismatches were found only by reading code: Quotes on Timesheets'
   `version`, Booking on Hiring's `v`, and Quotes on Clients' amount unit.
2. **Event types tied to their emitter,** or a `from` option on `handle`, so tools need
   not check `source` by hand.
3. **An `amount` kind in event data** (`{value, currency}`, as `actions` has), and a
   list kind.
4. **A seal for "these roles or this member".**
5. **Realtime join rules by groups or audience column,** and a feed to a per-member
   channel.
6. **The fake:**
   - It answers every `emit` "0 receivers"; an option to say N is needed.
   - It turns no database write into a feed event.
   - It reads `former` once at start.
   - Its `membership` callback is synchronous.
   - Its notification pacing folds items and loses their keys.
7. **An SDK helper to strip format characters** from event text.
8. **The PR itself:**
   - `contract/README.md:36` still shows contract 0.5.
   - `package.json` `files` omits `client/src/actions.ts` and
     `client/src/testing-folders.ts`.
   - `reference/sdk` (PR #9, `2581b22`) is older than the PR head `1a825a6`: it still
     has `chest.currency`, and lacks `actions` and `todo`.
9. **The time zone:** the PR removes only the ways to *set* a zone. `chest.timeZone`
   (the company's, captured once) and `member.timeZone` (the browser's) remain as
   read-only facts. If the owner wants zones wholly in the apps, `chest.timeZone` would
   go too. The tools would then need their own company-zone setting, as Status and
   Rooms already have.
